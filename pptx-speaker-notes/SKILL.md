# 撰写与修订 PPT 讲稿

以**用户最新上传的 PPTX** 为唯一编辑基准。旧版 PPTX 只用于辨认哪些 Notes 是用户后来改写的；不要凭旧版页码覆盖新内容，也不要恢复已删除的页。按当前任务决定讲稿语言；英文汇报通常写自然、可口述的英文。

## 首次写入 Notes

1. 以当前 PPTX 为准，清点页数、顺序、可见文字、图表、截图、动画和现有 Notes；渲染并实际查看每页。先判断哪些页需要正式口述，哪些是封面、目录、备用页或仅作过渡。已有的用户讲稿不要当作空白重写。
2. 从全套页面梳理汇报主线：为什么做、已有工作与新增内容、方法或产品演示、结果、局限和下一步。为每页记下一句“这页要让听众明白什么”，并核对它怎样承接上一页、引出下一页。缺少支撑的信息不要自行补成事实。
3. 对涉及项目实现、数据处理或工具能力的页面，按需读相关代码和文档，确认输入、关键步骤、输出与当前状态。区分已实现功能、示例画面、计划中的工作，以及统计证据和因果结论。只把与该页讲解有关的细节写进讲稿，不把代码清单搬进 Notes。
4. 逐页写自然可口述的讲稿：先给听众定位画面，再解释关键图表、数字或操作及其意义，最后用一句符合实际页序的话过渡。根据页面信息量给足解释，避免仅扩写标题；演示页按真实点击或动画顺序讲，出现后再解释隐藏的图。
5. 从头连续读一遍 Notes，检查术语、代词、时间状态、数字口径和页间衔接。听起来像重复模板的开头和 “On the next slide” 应改成具体的逻辑过渡；同一概念的首次介绍与后续回顾要有不同深度。

## 在用户修订后逐页对照

1. 清点当前页数与顺序，提取每页可见文字和 Notes，并渲染幻灯片。截图或图片页即使提取不到文字，也要实际查看。用页面内容而不是页码匹配旧版，记录新增、删除、合并和移位的页。
2. 将当前 Notes 与匹配的旧版比较，标出用户已改写的段落。默认原样保留用户的措辞和科学判断。若用户同时要求讲稿连贯，而改写后的 Notes 仍指向已删除的“下一页”或与当前画面冲突，只改这处必要的过渡或事实，保留其余内容。
3. 对每页核对讲稿是否讲到了该页的核心信息、图表和限制条件。不同截图若展示不同案例，不要把它们讲成同一次分析。若需要根据代码补充流程，先读相关实现；区分已实现功能、计划中的工作和实际观察到的结果。

## 两种情况都适用的写作原则

- 每页先说明听众正在看什么，再解释它回答的问题或关键细节，最后自然引出真正的下一页。口述语言应比幻灯片文字更流畅，但不能只复述标题。
- 需要报告数字时保留单位、分母和所指对象；不要把文献筛选数说成已导入数据，也不要把统计关联说成因果证明。
- 避免机械地在每页写 “On the next slide”。只有确认新页序后才使用明确的页间指代。对用户自己写的 Notes，优先补最短的衔接句。
- 代码路径或来源若需保存在 Notes，可放在单独的 `Code reference (not spoken):` 段落，不混进口述稿。

## 保存与核对

按可用的演示文稿工具编辑 Notes，并遵循 `presentations` skill 的导出与验证要求。编辑 Notes 的任务不要顺手改页面内容。若导入再导出导致原 PPTX 的动画、媒体或版面变化，且原文件对应的 Notes part 已存在，可用 [scripts/transfer_notes.py](scripts/transfer_notes.py) 将已写好的 Notes 段落移回原文件。该脚本只改选定 Notes part；如目标页没有 Notes part，应另选能完整保留 PPTX 结构的方法。

交付前逐项确认：页数和顺序与用户文件相同；每张正式汇报页 Notes 非空且对应画面；未指定修改的 Notes 保持原文；幻灯片视觉、动画和媒体与源文件一致。报告实际修改了哪些 Notes，并交付完整 PPTX。
